Boomi Process Design
Three shapes. Zero scripting. Cloud atom compatible. The simplest possible production OCR pipeline.
1

WSS Listener

Receives raw image binary via HTTP POST. Single-data input/output, text/plain response type. Endpoint: executeOcr

2

REST Connector

Forwards binary payload to DTAT-OCR at localhost:5002/ocr. Basic Auth, 10-min read timeout, Content-Type: image/png

3

Return Documents

Sends extracted text directly back to the HTTP caller. No transformation, no mapping — the OCR text IS the response.

Why this matters: Traditional Boomi OCR used Groovy shell execution + Node.js + Disk connectors — a 7-shape process that couldn't run on cloud atoms. This pattern uses standard REST connectors only, works on any atom type, and is maintainable by any Boomi developer.

What DTAT-OCR Does Behind the Scenes

Receive

Accepts raw image binary, detects file type from Content-Type header

Extract

Calls AWS Textract detect_document_text, returns structured blocks

Store

Saves document metadata + extracted content to SQLite database

Format

Returns text in Textract, Google Vision, Azure OCR, or native formats

AWS Textract processes documents in 1–3 seconds. Compare to 3–8 minutes with local AI models on CPU.
